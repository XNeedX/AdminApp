## User Scenarios & Testing *(mandatory)*

### User Story 1 - Create Doctor Profile with Valid Data (Priority: P1)

As a Receptionist signed in to the admin system, on the "Doctors" page, I want to open the doctor creation modal, fill in all required doctor information (and optionally attach a photo and middle name), and submit the form so that the doctor is added to the system and receives an email with auto-generated credentials.

**Why this priority**: This represents the core business value and primary workflow of the feature. Without successful creation and credential dispatch, no doctor can be onboarded into the system.

**Independent Test**: Can be tested independently by logging in as a Receptionist, navigating to the "Doctors" page, clicking "Create doctor", filling in all mandatory fields with valid values, and clicking "Confirm". Delivers immediate value by creating a doctor record and sending an automated welcome email with credentials.

**Acceptance Scenarios**:

1. **Given** a Receptionist is on the "Doctors" page, **When** they click the "Create doctor" button, **Then** a modal window for doctor creation opens displaying all required fields (first name, last name, middle name, date of birth, email, specialization, office, career start year, status, photo uploader) and footer buttons ("Confirm" disabled by default, "Cancel").
2. **Given** the doctor creation modal is open, **When** the Receptionist enters valid first name, last name, date of birth (<= current date), email, selects a valid specialization, office, career start year (<= current year), and leaves status as default "At work", **Then** the "Confirm" button becomes enabled.
3. **Given** all required fields are filled with valid values, **When** the Receptionist clicks "Confirm", **Then** the doctor profile is saved to the system, a system-generated password is created, an email with credentials is sent to the doctor's email, the modal closes, and the Receptionist is returned to the updated Doctors list.
4. **Given** the Receptionist uploads an optional photo and enters an optional middle name along with valid required fields, **When** they click "Confirm", **Then** the photo and middle name are successfully associated with the created doctor profile.

---

### User Story 2 - Field Validation on Blur & Submission Guarding (Priority: P2)

As a Receptionist filling in the doctor creation form, I want immediate contextual feedback when leaving an invalid or empty field (on blur) so that I can correct errors before submitting, and I expect the "Confirm" button to remain disabled while any required field is invalid or missing.

**Why this priority**: High priority for data integrity and UX. Prevents corrupted or incomplete doctor profiles from being submitted and guides the user with explicit error messages.

**Independent Test**: Can be tested by focusing and blurring each form control without entering data, entering malformed values, or selecting future dates, verifying that specific error messages appear immediately on blur and that "Confirm" remains disabled.

**Acceptance Scenarios**:

1. **Given** the First Name or Last Name field is touched and blurred while empty, **When** blur occurs, **Then** an inline error message is displayed: "Please, enter the first name" or "Please, enter the last name", and "Confirm" remains disabled.
2. **Given** the Date of Birth field is blurred while empty, **When** blur occurs, **Then** an inline error message is displayed: "Please, select the date", and dates later than the current date cannot be selected.
3. **Given** the Email field is blurred while empty, **When** blur occurs, **Then** the error "Please, enter the email" is displayed.
4. **Given** the Email field contains text without "@" or in an invalid format, **When** blurred, **Then** the error "You've entered an invalid email" is displayed.
5. **Given** the entered Email already belongs to an existing user in the system, **When** validated on blur, **Then** the error "User with this email already exists" is displayed.
6. **Given** the Specialization combobox is blurred with no selection, **When** blur occurs, **Then** the error "Please, choose the specialisation" is displayed; **Given** a custom typed text does not match any valid specialization, **When** blur occurs, **Then** the error "Invalid specialization name" is displayed.
7. **Given** the Office dropdown is blurred with no selection, **When** blur occurs, **Then** the error "Please, choose the office" is displayed.
8. **Given** the Career Start Year field is blurred without a selected year, **When** blur occurs, **Then** the error "Please, select the year" is displayed; years later than current year cannot be selected.
9. **Given** any required field is invalid or untouched, **Then** the "Confirm" action button remains strictly disabled.

---

### User Story 3 - Safe Cancellation Confirmation Flow (Priority: P3)

As a Receptionist working on the doctor creation form, I want a confirmation prompt when clicking "Cancel" so that I do not accidentally lose entered doctor data.

**Why this priority**: Guard against accidental data loss and provide clear escape hatches during data entry.

**Independent Test**: Can be tested by opening the form, entering partial or complete data, clicking "Cancel", verifying the confirmation dialog appears, and verifying both "Yes" (discard) and "No" (stay) actions.

**Acceptance Scenarios**:

1. **Given** the doctor creation modal is open, **When** the Receptionist clicks "Cancel", **Then** a confirmation dialog appears with the message: "Do you really want to cancel? Entered data will not be saved." with options "Yes" and "No".
2. **Given** the cancellation confirmation dialog is displayed, **When** the Receptionist clicks "No", **Then** the confirmation dialog closes and the Receptionist remains on the creation form with all previously entered data intact.
3. **Given** the cancellation confirmation dialog is displayed, **When** the Receptionist clicks "Yes", **Then** the confirmation dialog and the creation modal both close, all entered data is discarded, and the Receptionist is returned to the "Doctors" page.

---

### Edge Cases

- **Future Dates Boundary**: Date of Birth and Career Start Year must reject dates or years greater than the current date/year.
- **Career Start vs Date of Birth**: The career start year cannot be prior to the doctor's birth year.
- **Duplicate Email Detection**: Real-time or on-blur check must detect already registered emails and flag "User with this email already exists" prior to submission.
- **Specialization Filtering**: Typing in the combobox filters available specializations; if the user leaves the input with partial text that was not selected from the list, it flags "Invalid specialization name".
- **Network Disruption during Confirm**: If the network connection drops or the server encounters a transient error upon clicking "Confirm", an accessible error notification is displayed, entered data is preserved, and the "Confirm" button is re-enabled for retry.
- **Unsupported Photo File**: If a user attempts to upload an unsupported file format (non-image) or a file exceeding maximum size limits, an inline error is displayed and the file is not attached.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST allow signed-in Receptionists to trigger doctor creation via a "Create doctor" action on the "Doctors" page.
- **FR-002**: System MUST render the creation form inside an accessible modal dialog featuring a dedicated header, form body, and footer containing "Confirm" and "Cancel" buttons.
- **FR-003**: The form MUST include the following fields with their specified requirements:
  - Photo: File uploader (optional).
  - First Name: Single-line text input (required).
  - Last Name: Single-line text input (required).
  - Middle Name: Single-line text input (optional).
  - Date of Birth: Date picker (required; must be <= current date).
  - E-mail: Email text input (required; valid email format; must be unique in system).
  - Specialization: Combobox with type-to-filter capability (required; must match existing specialization item).
  - Office: Single-select dropdown (required).
  - Career Start Year: Year date picker (required; must be <= current year).
  - Status: Single-select dropdown (required; default value: "At work"; options: "At work", "On vacation", "Sick Day", "Sick Leave", "Self-isolation", "Leave without pay", "Inactive").
- **FR-004**: System MUST trigger validation and display error messages on control `blur` events:
  - First Name empty: `"Please, enter the first name"`
  - Last Name empty: `"Please, enter the last name"`
  - Date of Birth empty: `"Please, select the date"`
  - E-mail empty: `"Please, enter the email"`
  - E-mail invalid (no `@` or malformed): `"You've entered an invalid email"`
  - E-mail already registered: `"User with this email already exists"`
  - Specialization empty: `"Please, choose the specialisation"`
  - Specialization non-matching value: `"Invalid specialization name"`
  - Office empty: `"Please, choose the office"`
  - Career Start Year empty: `"Please, select the year"`
- **FR-005**: System MUST keep the "Confirm" button disabled whenever one or more required fields are empty, untouched, or invalid.
- **FR-006**: When "Confirm" is clicked with valid inputs, system MUST submit the doctor profile, generate a secure system password, persist the record, and trigger an automated credential email to the doctor's email address.
- **FR-007**: When "Cancel" is clicked on the creation form, system MUST display a confirmation dialog: `"Do you really want to cancel? Entered data will not be saved."` with "Yes" and "No" choices:
  - Selecting "Yes" MUST close all dialogs, discard entered state, and return the user to the "Doctors" page.
  - Selecting "No" MUST close the confirmation dialog and preserve all entered form state.

### Key Entities

- **Doctor Profile**: Represents the doctor's personal and professional identity. Attributes: first name, last name, optional middle name, optional photo, date of birth, email address, career start year, current working status, assigned office, and specialization.
- **Specialization**: Represents a medical discipline (e.g., Cardiology, Dermatology, Pediatrics) that can be searched and selected from predefined hospital specializations.
- **Office**: Represents a physical clinic room or office location assigned to the doctor.
- **Doctor Status**: Represents the operational availability of the doctor within the healthcare facility ("At work", "On vacation", "Sick Day", "Sick Leave", "Self-isolation", "Leave without pay", "Inactive").

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A receptionist can successfully complete and submit a doctor profile in under 2 minutes when having standard staff information ready.
- **SC-002**: 100% of invalid or omitted required fields trigger corresponding contextual error messages immediately upon `blur` and prevent form confirmation.
- **SC-003**: 100% of successful doctor creations result in an automated email dispatch containing system-generated credentials without manual staff intervention.
- **SC-004**: Zero accidental data losses occur from misclicks on "Cancel", guaranteed by mandatory cancellation confirmation prompts.
- **SC-005**: Future dates are 100% blocked from entry in both Date of Birth and Career Start Year fields.

## Assumptions

- **Photo Constraints**: Photo upload supports standard raster formats (JPEG, PNG, WebP) with a default maximum size limit of 5MB.
- **Career Start Logic**: Career start year cannot precede the doctor's birth year.
- **Email Dispatch Service**: Backend services handle credential generation and SMTP delivery asynchronously upon successful record creation.
- **Predefined Options**: Lists of active offices and specializations are preloaded from the system catalogs for selection in the modal.
