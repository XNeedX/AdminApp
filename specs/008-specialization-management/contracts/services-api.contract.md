# Contract: Services API Usage (generated client)

**Feature**: `008-specialization-management` | **Date**: 2026-11-18

The AdminApp does not define its own API contracts. Everything below maps to existing operations in
`src/app/api/generated/services/` (generated by `ng-openapi-gen` from
`openapi/services.openapi.json`). Paths are Gateway-relative:
`${environment.apiUrl}/services` + operation path.

---

## 1. Operations Consumed

| Operation | Generated method | HTTP | Request | Response (typed) |
|-----------|------------------|------|---------|------------------|
| List specializations | `SpecializationService.specializationGet({ Page, PageSize })` | `GET /Specialization` | `{ Page?: number; PageSize?: number }` | `ApiResponseOfPagedResultOfViewSpecializationListDto` |
| Get specialization | `SpecializationService.specializationIdGet({ id })` | `GET /Specialization/{id}` | `{ id: string }` | `ApiResponseOfViewSpecializationDto` |
| Create specialization | `SpecializationService.specializationPost({ body })` | `POST /Specialization` | `{ body?: CreateSpecializationCommand }` | `void` (see G-2) |
| Update specialization | `SpecializationService.specializationIdPut({ id, body })` | `PUT /Specialization/{id}` | `{ id: string; body?: EditSpecializationDto }` | `void` |
| Change specialization status | `SpecializationService.specializationIdStatusPatch({ id, body })` | `PATCH /Specialization/{id}/status` | `{ id: string; body?: EditStatusDto }` | `void` |
| Create service | `ServiceService.servicePost({ body })` | `POST /Service` | `{ body?: CreateServiceCommand }` | `ApiResponseOfGuid` |
| Update service | `ServiceService.serviceIdPut({ id, body })` | `PUT /Service/{id}` | `{ id: string; body?: EditServiceDto }` | `void` |

Rules:

- No other HTTP call is added. No `HttpClient` usage outside `api/generated`.
- All responses are treated as `unknown` until narrowed by the envelope helpers before mapping
  (`readApiEnvelope` / explicit guards), because generated fields are optional.
- Authorization is already enforced by `auth.interceptor` and route `roleGuard('Receptionist')`.

---

## 2. Envelope Handling

| Kind | Generated shape | Handling |
|------|-----------------|----------|
| Read | `{ isSuccess?, message?, errors?, data? }` | Validate success + payload shape; on shape error show "The specialization data returned by the API is incomplete." |
| Command with body | `{ isSuccess?, message?, errors?, data?: Guid }` | Read `data`; missing id after `servicePost` is a contract error (do not close the dialog) |
| Command without body | `void` | Success = HTTP completion; body is ignored |

Error messages come from `extractErrorMessage(HttpErrorResponse)` so the API's validation messages
surface unchanged.

---

## 3. Payload Mapping

### Specialization create (target state, gate G-1)

```json
{
  "name": "Cardiology",
  "status": 0
}
```

### Specialization create (current generated contract - blocked)

```json
{
  "name": "Cardiology",
  "price": <required, > 0>,
  "category": <required enum>,
  "status": 0
}
```

The frontend must not invent `price`/`category`. Until the backend contract drops them, create and
edit are blocked (plan.md G-1).

### Specialization update

Same shape as create, plus `id` in the path.

### Status change

```json
{ "status": 1 }
```

`0` = Active, `1` = Inactive (generated `Status`).

### New service row

```json
{
  "name": "Blood test",
  "price": 12.5,
  "category": 0,
  "status": 0,
  "specializationId": "<specialization id>"
}
```

### Existing service row

```json
{ "name": "Blood test", "price": 12.5, "category": 0, "status": 0 }
```

### Constraints carried from the UI

- `name`: trimmed, non-empty, <= 100 characters.
- `price`: > 0, at most two fractional digits.
- `category`: `0 | 1 | 2`.
- `status`: `0 | 1`.
- At least one service row per submission.

## 4. Ordering and Failure Semantics

| Flow | Sequence | On failure |
|------|----------|------------|
| Create | `specializationPost` -> `servicePost` (row 1..n, sequential) | Stop at first failure; retain form values and the created specialization id; retry updates instead of re-creating |
| Edit | `specializationIdPut` -> `serviceIdPut` (existing rows) -> `servicePost` (new rows) | Stop at first failure; retain form values and created service ids; retry skips completed work |
| Status (list or View mode) | `specializationIdStatusPatch` | Restore previous radio value; show error; no client-side cascade |
| List | `specializationGet` | Show retryable error state |
| Detail | `specializationIdGet` | 404 -> "Specialization not found" with a way back; other errors -> retry |

There is no delete operation for stored services; the frontend never attempts one (FR-037).

---

## 5. Contract Gaps

| Id | Gap | Frontend consequence | Owner |
|----|-----|----------------------|-------|
| G-1 | Specialization payload requires `price` + `category`; the spec defines only `name` + `status` | Create/edit cannot be submitted without fabricating data | Backend contract change + client regeneration |
| G-2 | `POST /Specialization` returns `void` in the generated client although the endpoint responds `201` with `ApiResponse<Guid>` | Cannot obtain the new id to attach services | Backend `[ProducesResponseType]` or extend `scripts/augment-services-openapi.mjs` |
| G-3 | `PUT /Specialization/{id}` and `PATCH /Specialization/{id}/status` declare no success response | Success is inferred from HTTP status only | Same as G-2 (cosmetic, non-blocking) |
| G-4 | No backend cascade from specialization status to services and doctors | US5 AC-2 / SC-006 fail end-to-end although the UI behaves correctly | Backend |
| G-5 | No service delete operation | "Discard row" is limited to rows added in the current session, as specified | Accepted, matches FR-037 |

Regeneration command after the backend or overlay changes:
`npm run api:services` (runs the overlay script, then `ng-openapi-gen`).
